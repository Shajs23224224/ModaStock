## 1. Propósito

Este documento presenta la herramienta seleccionada para gestionar los requisitos de ModaStock, la forma de organizar su uso y la trazabilidad de los requisitos registrados. El instrumento de evaluación establece dos indicadores: seleccionar una herramienta de gestión de requisitos de acuerdo con la metodología elegida y utilizarla adecuadamente para gestionar el proyecto.

## 2. Descripción del proyecto

ModaStock es un sistema web de gestión de inventario especializado en tiendas y marcas de ropa. Busca administrar productos, referencias y variantes por talla y color, consultar existencias y registrar entradas, salidas y ajustes de inventario con trazabilidad.

El repositorio contiene documentación de análisis y requisitos en `docs/fase-1/`, además de componentes frontend y backend. Su README describe React, TypeScript, Vite, Python, FastAPI, SQLAlchemy, Alembic y PostgreSQL, así como pruebas automatizadas y contenedores Docker. Esta descripción corresponde a la documentación del repositorio; no constituye por sí misma una comprobación de despliegue en producción.

## 3. Metodología de trabajo propuesta

Para organizar el backlog de requisitos se propone utilizar Scrum como marco ágil de referencia. El catálogo se administra como Product Backlog; durante la planificación se seleccionan los requisitos que serán atendidos en un Sprint y se trasladan al Sprint Backlog. Los criterios de aceptación permiten comprobar el cumplimiento de cada requisito.

La hoja de ruta del proyecto conserva sus diez fases. Scrum se plantea como mecanismo iterativo de planificación y seguimiento dentro de esas fases, no como sustituto de la hoja de ruta. La documentación actual del repositorio describe las fases, pero no formaliza por sí misma una metodología ágil; por eso la adopción definitiva de Scrum debe ser coherente con la decisión metodológica académica del proyecto.

## 4. Herramienta seleccionada: GitHub

Se selecciona GitHub porque el repositorio de ModaStock ya se encuentra alojado en esta plataforma y permite mantener la gestión de requisitos vinculada al código y a la documentación.

- **GitHub Repository:** centraliza código fuente, documentos y versiones.
- **GitHub Issues:** registra cada requisito como un elemento independiente con descripción, prioridad, criterios de aceptación y observaciones.
- **GitHub Projects:** permite organizar visualmente los Issues, priorizar el backlog y supervisar el avance por estados.

## 6. Procedimiento de gestión y validación

1. Identificar la necesidad del comercio y redactarla como requisito funcional o no funcional.
2. Asignar un identificador único (RF o RNF), una descripción y una prioridad.
3. Definir criterios de aceptación observables y verificables.
4. Crear o actualizar el Issue correspondiente en el repositorio ModaStock.
5. Revisar el requisito con el cliente o un usuario representativo para detectar ambigüedades, contradicciones u omisiones.
6. Priorizar los elementos del Product Backlog y seleccionar los que se atenderán durante el Sprint.
7. Implementar y probar el requisito, adjuntando resultados y vinculando los cambios de código.
8. Cambiar el estado a Hecho únicamente cuando todos los criterios de aceptación hayan sido verificados y no queden defectos bloqueantes.

## 7. Estructura propuesta del tablero GitHub Projects

El tablero visual debe configurarse con los siguientes estados:

| Estado | Criterio de uso |
|---|---|
| Product Backlog | Requisitos registrados, priorizados y pendientes de selección para un Sprint. |
| Sprint Backlog | Requisitos seleccionados para el Sprint vigente. |
| En desarrollo | Requisitos cuya implementación está en curso. |
| En revisión y pruebas | Requisitos cuya solución se revisa contra los criterios de aceptación. |
| Hecho | Requisitos implementados y verificados con evidencia. |

Campos recomendados: identificador, tipo (funcional/no funcional), prioridad, Sprint, estado, criterios de aceptación y enlace a evidencia.
